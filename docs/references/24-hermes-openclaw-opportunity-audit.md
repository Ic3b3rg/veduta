## Correction to Veduta's earlier competitor thesis

Veduta's [README thesis](../../README.md), [Architecture §1](../../ARCHITECTURE.md), [ADR-0001](../adr/0001-home-first.md), [Research 01](./01-sota-hermes-openclaw.md), and [Research 02](./02-competitor-home-first.md) should be treated as **date-bound or stale on OpenClaw's visual persistence**. They describe its Canvas/A2UI experience as a per-session response or secondary, ephemeral visual workspace and call the territory open. OpenClaw now documents **core Session Dashboards**: each thread owns a board; the board and its widgets survive `/new` and `/reset`, persist on the Gateway, appear across devices, and are removed when the owning thread is deleted. Agents can create and update named widgets in place. Boards can contain native reports, sandboxed custom HTML/JS, MCP apps, browser views, and A2UI widgets. ([Session Dashboards](https://docs.openclaw.ai/web/dashboards))

This does **not** make the two product models identical. OpenClaw's board is **thread-owned**; Veduta's intended Surface is **Space-owned**, part of a life area's durable, validated Atom tree and typed state, with a deterministic fast path and a Space Event log ([Veduta vocabulary](../../CONTEXT.md), [Architecture §2–3](../../ARCHITECTURE.md)). That is a specific architectural and user-experience claim to demonstrate in the product, not an unoccupied category of “persistent UI.” OpenClaw's free-form HTML/JS widgets are also incompatible with Veduta's current anti-requirement against Agent-generated markup; copying them is not a parity recommendation ([Architecture §7](../../ARCHITECTURE.md), [OpenClaw widget contract](https://docs.openclaw.ai/web/dashboards)).

Hermes's official Plugin Catalog now lists the **community** `home-dashboard` plugin, added 2026-09-16. Its own reviewed README describes a persistent, customizable Home tab for Hermes Web and Desktop with 16 fixed widgets for host status, sessions, cron, logs, notes, timers, and similar controls. It polls existing host APIs and saves layout in the plugin directory. This further weakens any claim that competitors have no Home-like view. It is still an optional operational/plugin page of fixed widget types, rather than evidence of Agent-authored, Space-owned Surfaces for life areas. ([Hermes catalog entry and reviewed plugin README](https://hermes-agent.nousresearch.com/docs/plugins/home-dashboard))

The August Hermes studies remain useful but are revision-specific. [Research 19](./19-hermes-chat-directed-extensibility.md) and [Research 21](./21-hermes-custom-mcp-from-chat.md) establish what their inspected revisions supported; they should not be read as a September guarantee that chat-directed connection behavior has not changed. Current Hermes documentation describes `manage_connections` for managed connectors and catalog MCP setup, including an approval/setup card and same-turn tool use in supported clients. Arbitrary MCP servers, Skills, and plugins have additional configuration or installation paths, so this is a substantial common connection flow, not one universal installer for every extension type. ([Hermes tool reference](https://hermes-agent.nousresearch.com/docs/reference/tools-reference), [Hermes MCP guide](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp/), [Hermes Skills guide](https://hermes-agent.nousresearch.com/docs/guides/work-with-skills), [Hermes plugin guide](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins))

## Research judgment for prioritization

The strongest shared pattern is a short path from installation to a useful action, then repeat use through familiar communication channels, Skills/integrations, memory, and scheduled work. These are **plausible** adoption levers because both products visibly invest in them; the available first-party sources do not measure their contribution to growth. The open requests particularly stress backup/recovery, cross-device continuity, mobile friction, secret handling, execution boundaries, and memory quality. ([OpenClaw getting started](https://docs.openclaw.ai/getting-started), [Hermes quickstart](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart/), [issue table](#representative-github-feature-requests))

For Veduta, the high-value hypothesis is **one Agent, one Space-owned living visual state per life area, with trusted changes and recovery across devices**. It needs to be experienced end to end: install, first useful Surface, refresh/reconnect, an Automation outcome, and a reversible decision. The competitor evidence makes the Home model more demanding to prove, because OpenClaw now has durable thread boards; it does not imply copying multi-agent rosters, free-form HTML/JS, provider-native Bridge UI, or other choices excluded by [Architecture §7](../../ARCHITECTURE.md). A ranked Veduta backlog still requires checking its current implementation and canonical GitHub issues against each proposed item.

## Integration-platform follow-up: one user journey, many external capabilities

The relevant competitive advantage is the **range of tasks that become possible after connecting a service**. A Gmail checkbox alone does not create that range. The technical extension mechanisms are different, but users should be able to discover, connect, verify, use, reconnect, and remove external capabilities through a coherent product journey. This is a product hypothesis, not a measured explanation for either competitor's growth.

**Recommended product contract to specify:** the user asks to connect Gmail, GitHub, Linear, a calendar, or another service from Chat or the PWA; Veduta shows the supported method, requested access, and what the Agent can do; the user authorizes through a credential-safe flow; Veduta probes the connection and shows a real first capability; the Agent can use it in the same job; the user can later inspect, reconnect, restrict, and remove it. Connections may be Gateway-wide as [#121](https://github.com/Ic3b3rg/veduta/issues/121) specifies for Gmail, while each Space's use and resulting Event/Surface ownership remain explicit. The user-facing flow can be shared even if a first-party Skill, native API, CLI, or future MCP server performs the work behind it. This should be measured by time to first successful task, supported task breadth, permission clarity, and successful reconnection after restart, rather than a catalog count. ([ADR-0026](../adr/0026-skills-may-drive-general-tool-execution.md), [Architecture §3](../../ARCHITECTURE.md))

The existing [Mailbox roadmap](https://github.com/Ic3b3rg/veduta/issues/135) is a useful first test because Gmail and Himalaya must produce the same user-facing Mailbox result through different mechanisms. It does not specify a general cross-service connection journey, MCP client, or third-party extension lifecycle. The near-term path is to make first-party Skill/general execution and several end-to-end connections work, then specify a Veduta-owned MCP path for wider service reach. A third-party plugin marketplace would change the current v1 scope and needs a separate decision. [Hermes #95916](https://github.com/NousResearch/hermes-agent/issues/95916) asks for one reusable composition of Skill, MCP, plugin, and credential requirements; [OpenClaw #112077](https://github.com/openclaw/openclaw/issues/112077) asks to move delegated conversational setup to a protected human UI. They are direct demand signals for this workflow, not evidence of measured adoption or a claim that the competitors lack their existing connection tools. [OpenClaw #104312](https://github.com/openclaw/openclaw/issues/104312) also asks to scope MCP activation as catalogs grow. The older [#76493](https://github.com/openclaw/openclaw/issues/76493) must not be read as proof that current OpenClaw requires plaintext MCP secrets: [current MCP docs](https://docs.openclaw.ai/tools/mcp) prescribe supported secret mechanisms.

**Sequence matters.** OpenClaw's [founder reported more than 100,000 stars on 2026-01-29](https://openclaw.ai/blog/introducing-openclaw), months before its 2.0 and September plugin releases. Hermes already listed broad channels, MCP, and Skills in March; its unified connector cards appeared in September. The later release notes show continuing investment in easier setup, discovery, authorization, immediate use, visual work, and recovery. They do **not** establish which features caused the initial growth. ([Hermes v0.2.0](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.3.12), [Hermes v0.21.4](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.9.21), [OpenClaw v2026.9.5](https://docs.openclaw.ai/releases/2026.9.5))

**Ranking effect:** this audit reinforces opportunity **#3** as a general connection lifecycle rather than a count of integrations, and strengthens **#4** first-run setup, **#5** recovery/continuity, and **#8** an honest, demonstrable release story. It does not displace **#1–#2**: if Veduta cannot make accepted, Space-owned Surfaces true and useful on Home, extra external tools do not deliver its proposed daily-use advantage. Hermes's release notes also show why Veduta should not turn every integration into a Skill: Spotify moved to a native plugin and Linear to MCP in [v0.16.0](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.6.5). The common user journey can span different mechanisms.

## Ranked Veduta opportunities

This order weighs a credible daily-use advantage and the leverage of a reusable connection path over isolated feature breadth. It distinguishes a present implementation from an accepted design or an open issue. Issue state was checked on 2026-09-28 and relevant integration issues again on 2026-09-29; an open parent may contain completed slices. These are research priorities, not new issue specifications.

1. **Make every accepted Surface visibly true and operable.** A created plan must have content, a recorded measurement must change its visible record and chart, and an Add action must change its collection after reload. Veduta's own [#140](https://github.com/Ic3b3rg/veduta/issues/140) documents empty, inert, and stale accepted Surfaces; [#150](https://github.com/Ic3b3rg/veduta/issues/150) closes the semantic contract, [#161](https://github.com/Ic3b3rg/veduta/issues/161) defines real deterministic fast-path mutations, and [#156](https://github.com/Ic3b3rg/veduta/issues/156) makes the Surface/Event outcome recoverable. This is the first proof required before claiming an advantage over [OpenClaw's already persistent and interactive dashboards](https://docs.openclaw.ai/web/dashboards).

2. **Make Home useful without asking the Agent anything, including on a phone.** The Home grid and routed Space drill-down already landed in [#64–#66](https://github.com/Ic3b3rg/veduta/issues/33); remaining [Pending-decision placement](https://github.com/Ic3b3rg/veduta/issues/67), [new-activity signals](https://github.com/Ic3b3rg/veduta/issues/68), [narrow-screen journey](https://github.com/Ic3b3rg/veduta/issues/69), and the approved [state-led visual contract](https://github.com/Ic3b3rg/veduta/issues/157) determine whether opening Veduta gives a better life-area view than browsing [thread-owned boards](https://docs.openclaw.ai/web/dashboards). Test freshness and attention with real changing data, not a polished static seed.

3. **Make many external services connectable through one coherent user journey.** This has greater reach than adding Gmail, Calendar, and other forms one by one. The near-term foundation is the accepted [Skill/general-execution design](../adr/0026-skills-may-drive-general-tool-execution.md) and open [#122](https://github.com/Ic3b3rg/veduta/issues/122)/[#123](https://github.com/Ic3b3rg/veduta/issues/123); the missing product specification is a cross-service flow for discovery, protected authorization, capability review, live verification, same-job use, reconnection, and removal. Use Gmail and generic IMAP as the first distinct execution mechanisms behind a shared Mailbox outcome, then test a non-mail service. A Veduta-owned MCP client is the next candidate for broad external reach and needs its own decision and issue; provider-native MCP remains disabled in the current [AgentRunner boundary](../../ARCHITECTURE.md). Third-party plugin distribution requires a separate scope decision. Both competitors already have substantial [chat-directed connection](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp/) and [in-product plugin/MCP setup](https://docs.openclaw.ai/web/control-ui/settings), so the differentiator must be a simpler, trustworthy lifecycle connected to Space-owned Surfaces, not the mere existence of connectors. ([Integration-platform analysis](#integration-platform-follow-up-one-user-journey-many-external-capabilities))

4. **Turn a clean install into one useful Space and Surface in under 15 minutes.** Veduta already has an [installer](../../deploy/README.md), [onboarding](https://github.com/Ic3b3rg/veduta/issues/19), and [Hermes/OpenClaw importer](https://github.com/Ic3b3rg/veduta/issues/20). The remaining [guided no-domain VPS path](https://github.com/Ic3b3rg/veduta/issues/48), [private phone access](https://github.com/Ic3b3rg/veduta/issues/49), and [onboarding restart repair](https://github.com/Ic3b3rg/veduta/issues/36) create the adoption path that the [Hermes](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart/) and [OpenClaw](https://docs.openclaw.ai/getting-started) quickstarts make prominent. Verify the first Agent action and Surface, not just service installation.

5. **Keep visible work continuous across reload, restart, and devices.** The PWA still has an [80-entry browser-local chat history](../../packages/pwa/src/pwa-storage.ts); Veduta's [#141](https://github.com/Ic3b3rg/veduta/issues/141) and [#149–#155](https://github.com/Ic3b3rg/veduta/issues/154) specify Gateway-owned Chat timelines, retry, pagination, and one client live-state authority. The high-engagement Hermes [cross-device request](https://github.com/NousResearch/hermes-agent/issues/20510) and OpenClaw's [cross-device boards](https://docs.openclaw.ai/web/dashboards) show the expected continuity. Prove one long turn survives a client reload and another device sees the same committed outcome without duplicate effects.

6. **Make proactive work real and visibly worth the cost.** Veduta already has a [scheduler](https://github.com/Ic3b3rg/veduta/issues/11) and [Space-owned Automation outcomes](https://github.com/Ic3b3rg/veduta/issues/91), but [#38](https://github.com/Ic3b3rg/veduta/issues/38) records model-completion stand-ins in core proactive paths. A [goal-directed Website monitor](https://github.com/Ic3b3rg/veduta/issues/92) and [exact-scope Mailbox Automation](https://github.com/Ic3b3rg/veduta/issues/126) can prove a confirmed rule updates the same Surface after restart, with unchanged checks advancing freshness rather than producing noise. This is Veduta's distinctive answer to [Hermes cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron/) and [OpenClaw Automations](https://docs.openclaw.ai/automation).

7. **Ship integrations as outcomes, not connection screens.** Complete the [passive Gmail connection](https://github.com/Ic3b3rg/veduta/issues/121), [bounded search and summary](https://github.com/Ic3b3rg/veduta/issues/122), [generic IMAP/SMTP work](https://github.com/Ic3b3rg/veduta/issues/123), and [approved threaded reply](https://github.com/Ic3b3rg/veduta/issues/125) into Space-owned Mailbox Surfaces; pair these with a confirmed [Website monitor](https://github.com/Ic3b3rg/veduta/issues/92). The differentiator is a useful result still visible tomorrow, consistent with Veduta's [pull-based personal Mailbox contract](../adr/0024-pull-based-personal-mailbox.md). Both competitors emphasize [broad tool reach](https://hermes-agent.nousresearch.com/docs/user-guide/features/tools/) and [integrations](https://docs.openclaw.ai/tools/plugin), so a bare OAuth success is insufficient.

8. **Publish a repeatable product demonstration and a release that matches it.** The [README](../../README.md) currently explains architecture and development but does not show a complete first-day user journey; the newest listed public release is [v0.0.5 from 2026-08-10](https://github.com/Ic3b3rg/veduta/releases/tag/v0.0.5), while substantial later work is tracked in the [issue history](https://github.com/Ic3b3rg/veduta/issues). Record a short clean-install demonstration that shows a living Surface, a fast-path interaction, an Automation update, and refresh on a phone; publish it only when those paths are truthful. Write feature-level release notes with links to those verified journeys and their recovery paths. [OpenClaw's first-party showcase](https://openclaw.ai/showcase) and [Hermes user stories](https://hermes-agent.nousresearch.com/docs/user-stories) illustrate how concrete jobs make a broad Agent comprehensible; their [milestone changelogs](#milestone-release-and-changelog-audit-2026-09-29) show how those journeys are presented release by release, without establishing a conversion rate.

9. **Add the first messenger Bridge as a return path to Home.** [ADR-0028](../adr/0028-concrete-bridge-extension-seam.md) deliberately waits for a concrete provider and commits only to bidirectional text, notifications, and Home deep links. Telegram is the first post-v1 target in the [PRD](../../PRD.md); no dedicated implementation issue appeared in the audited Veduta issue list. Both competitors already reach [messaging channels](https://hermes-agent.nousresearch.com/docs/user-guide/messaging), and OpenClaw's founder says its original project was a [WhatsApp Relay](https://openclaw.ai/blog/introducing-openclaw). This is an acquisition hypothesis, not evidence that messenger reach alone caused its growth.

10. **Give the Agent an authorized Web research or browser path for explicit requests.** Veduta's [Website monitor](https://github.com/Ic3b3rg/veduta/issues/92) is deliberately limited to approved public hosts and is not general Web search. [Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/features/browser) and [OpenClaw](https://docs.openclaw.ai/tools/browser/agent-tools) expose browser work, and an [OpenClaw request](https://github.com/openclaw/openclaw/issues/41120) illustrates its runtime cost. A later Veduta-owned capability should start with one bounded read/research journey, explicit origin handling, and result-to-Surface persistence. It must not silently turn provider-native browsing on.

11. **Make trust decisions and failures understandable in the PWA.** The [trust layer](https://github.com/Ic3b3rg/veduta/issues/14) and [Pending-decision contract](https://github.com/Ic3b3rg/veduta/issues/96) exist, while [chat resolution](https://github.com/Ic3b3rg/veduta/issues/98) and the [Trace console](https://github.com/Ic3b3rg/veduta/issues/81) remain open. A user should see what action awaits approval, which meaningful step failed, and what can be retried without reading `journalctl`. Requests for [Hermes Gateway permission tiers](https://github.com/NousResearch/hermes-agent/issues/527) and [OpenClaw execution restrictions](https://github.com/openclaw/openclaw/issues/7722) show that control remains a live concern in this category.

12. **Make backup and restore a practiced user journey.** Veduta has an [encrypted backup implementation](../../packages/daemon/src/backup.ts), but this audit found no dedicated open issue for guided recurring backup, portable restore, and a clean-machine rehearsal. Hermes users explicitly request [automatic backup and version history](https://github.com/NousResearch/hermes-agent/issues/12238); OpenClaw documents [backup and restoration](https://docs.openclaw.ai/install/backups). Demonstrate restoration of Spaces, Surfaces, FACTS, Model connections, and Automation state before promising durable personal ownership.

Do **not** count already completed imports, the Home grid, ChatGPT-subscription inference, the scheduler, or the existing backup engine as wholly missing. New marketplace, persistent agent hierarchy, free-form Agent HTML, voice, and provider-native rich Bridge views conflict with the present [v1 boundary](../../ARCHITECTURE.md) or require a later accepted decision.

## Mailbox is one integration family, not the extension architecture

- **Hermes has distinct email mechanisms.** Managed Gmail tools can come from the Nous connector gateway; the bundled Google Workspace Skill guides OAuth setup through chat but still requires a Google Cloud project, enabled APIs, credentials, and browser consent; the Himalaya Skill drives an external IMAP/SMTP CLI for mailbox tasks. Its Email gateway adapter instead lets a person _chat with Hermes by email_. These are different transports and permission models behind superficially similar “email” requests. [Connector tool reference](https://hermes-agent.nousresearch.com/docs/reference/tools-reference), [Google Workspace Skill](https://hermes-agent.nousresearch.com/docs/user-guide/skills/google-workspace), [agent mailbox guide](https://hermes-agent.nousresearch.com/docs/guides/agent-email-address), [Email gateway adapter](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/email).
- **OpenClaw also separates mail use cases.** Its Gmail Pub/Sub ingestion is a webhook/automation transport configured with `openclaw webhooks gmail setup`; its IMAP email trigger is a plugin with account configuration. Its general plugin and MCP systems can provide other mail operations, depending on the selected package or server. Neither documented trigger setup establishes a universal “connect Gmail entirely by chat” flow. [Gmail Pub/Sub trigger](https://docs.openclaw.ai/automation/cron-jobs/gmail), [webhooks CLI](https://docs.openclaw.ai/cli/webhooks), [IMAP email trigger](https://docs.openclaw.ai/automation/imap), [plugin capabilities](https://docs.openclaw.ai/plugins).

## Implications for Veduta — inference, not competitor fact

The reusable product unit should be a **connection lifecycle** across many services: discover a capability from a user goal; identify its execution mechanism (managed API, MCP server, Skill/CLI, or native provider adapter); collect secrets and OAuth outside the model transcript; show scopes and required actions; verify live tools; use them in the same requested job when ready; report failure, reconnection, and removal. Gmail/IMAP can test two mechanisms, while a non-mail service tests whether the flow is genuinely general. This is an inference from the distinct mechanisms and partial chat flows above, not evidence that either competitor has solved every step uniformly. It should be judged against Veduta's own architecture and issue specifications before becoming an implementation proposal.

“Configure it through chat” is a useful entry and orchestration pattern, but the inspected sources support a narrower claim: chat may discover, initiate, and resume connection work while an authenticated UI, OAuth browser, CLI, or explicit configuration still handles some steps. For Veduta, a truthful user journey should say which steps are possible in chat, which require a secure form or browser, and when a connection has actually passed a live capability check.

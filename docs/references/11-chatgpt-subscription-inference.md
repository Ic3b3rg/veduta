# ChatGPT subscription inference through Codex

Research for [Verify the supported ChatGPT subscription inference path](https://github.com/Ic3b3rg/veduta/issues/52), performed on 2026-08-05. The current published npm versions of both `@openai/codex` and `@openai/codex-sdk` were `0.146.1`; OpenAI source was inspected at commit [`9d00bb0`](https://github.com/openai/codex/tree/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c). Because Codex changes quickly, implementation must pin a version and generate protocol schemas from that same binary.

## Decision-grade answer

OpenAI supports a custom product integrating **Codex App Server**. It explicitly describes App Server as the interface for deep integrations in a product, including authentication and streamed Agent events. For a TypeScript Gateway, the supported local boundary is therefore a pinned [`@openai/codex`](https://www.npmjs.com/package/@openai/codex) binary running `codex app-server` over stdio, with the Gateway speaking its stable JSON-RPC surface. Stdio is supported; App Server's TCP WebSocket listener is explicitly experimental and unsupported. The binary can generate TypeScript or JSON Schema artifacts that match its exact version. [OpenAI's App Server documentation](https://developers.openai.com/codex/app-server) and [the versioned source protocol](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L20-L83) document this path.

However, this is a **Codex Agent** boundary, not a raw model-inference boundary. Its public primitives are threads, turns, items, approvals, tool progress, and possible side effects. OpenAI documents the Codex SDK for coding-focused Codex threads and describes it as embedding the Codex Agent in applications. No first-party documentation or public package found in this research exposes ChatGPT subscription credentials as a general Responses API credential or a tool-neutral inference client. The only source-level API that accepts caller-supplied ChatGPT tokens is marked **unstable, for OpenAI internal use only, do not use**. [App Server's Agent primitives](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L66-L83), [the SDK scope](https://developers.openai.com/codex/sdk), and [the internal-token warning](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server-protocol/src/protocol/v2/account.rs#L58-L101) establish that boundary.

Therefore [Model connections: Claude and ChatGPT subscriptions in the PWA](https://github.com/Ic3b3rg/veduta/issues/47) is **not implementable as written**. Its ChatGPT path simultaneously requires subscription-backed inference and forbids delegating Agent turns or tools to Codex. One of these must change:

1. Allow a ChatGPT connection to implement `AgentRunner` with Codex App Server owning the inner turn, then separately prove that Veduta can preserve its single Agent semantics, Event log duties, and tool/security boundary; or
2. Keep the current “subscription supplies inference only; Veduta owns the loop” boundary and mark ChatGPT subscription unavailable. Under that boundary, the supported OpenAI connection remains API-key BYOK.

Calling private ChatGPT backend routes, copying Codex's OAuth client identity into a custom OAuth implementation, extracting tokens from `auth.json`, or using `chatgptAuthTokens` would cross the documented support boundary.

## Exact supported client and API

### Recommended for this TypeScript repository

- Pin `@openai/codex` as a runtime dependency and launch `codex app-server` as a child process.
- Use the default stdio JSONL transport. Do not expose App Server directly to the browser or use its unsupported TCP WebSocket listener.
- At build time, run `codex app-server generate-ts` or `generate-json-schema` from the pinned binary, then validate every message against that version's schema. OpenAI says generated schemas are version-specific and guaranteed to match the binary. [Protocol and schema documentation](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L20-L64).
- Identify Veduta through `initialize.clientInfo`. OpenAI asks new enterprise-facing integrations to contact it so the client can be recognized in compliance logs. [Client identification requirements](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L119-L123).

`@openai/codex-sdk` is **not** the connection-management API needed by the issue. The TypeScript SDK wraps `codex exec`, and its public `Codex` class exposes starting and resuming Agent threads, not login, logout, account state, or model listing. [TypeScript SDK README](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/sdk/typescript/README.md#L1-L36) and [public class](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/sdk/typescript/src/codex.ts#L6-L38).

The official `openai-codex` Python SDK does expose browser login, device-code login, account refresh, logout, model listing, and turns, but it is currently beta and would add Python to this pnpm TypeScript deployment. It is useful as an executable specification, not the natural Veduta dependency. [Python SDK API reference](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/sdk/python/docs/api-reference.md#L49-L75).

## Authorization lifecycle

### Remote VPS flow

Use App Server's managed device-code flow:

1. The authenticated PWA asks the Gateway to start authorization.
2. The Gateway calls `account/login/start` with `type: "chatgptDeviceCode"`.
3. App Server returns `loginId`, `verificationUrl`, and a one-time `userCode`; the PWA displays those values.
4. The user signs in on OpenAI's page and enters the code. App Server polls and emits `account/login/completed`, followed by `account/updated` with the ChatGPT plan type.

The frontend-owning UX is explicitly documented by OpenAI. Device-code login is nevertheless **beta** and must first be enabled in personal ChatGPT security settings or by the workspace administrator. If it is disabled, there is no documented, token-free, no-terminal fallback suitable for a remote VPS. [App Server device-code contract](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L2268-L2287) and [headless-login prerequisites](https://developers.openai.com/codex/auth#login-on-headless-devices).

The browser flow is supported for a locally running Codex client, but its authorization URL redirects to `http://localhost:<port>/auth/callback`, hosted by App Server. In a browser visiting a remote Veduta PWA, `localhost` is the user's device, not the VPS. Without port forwarding or another terminal/network step, this cannot complete the required remote journey. The hosted success page changes only the post-success page; it does not relocate the callback. [Browser-flow contract](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L2223-L2242). This network conclusion is an inference from the documented redirect URI.

### Storage, refresh, and logout

- In managed ChatGPT mode, Codex owns the OAuth flow and refresh tokens, persists them, and refreshes them automatically. `account/read` reports account and plan state; `refreshToken: true` requests a proactive refresh. [Auth/account API](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/README.md#L2150-L2201).
- Codex can store credentials in `CODEX_HOME/auth.json` or an OS credential store. File storage is plaintext and OpenAI says to treat it like a password. On a headless VPS, Veduta cannot assume a keyring exists. [Credential storage](https://developers.openai.com/codex/auth#credential-storage).
- Current source proactively refreshes near expiry and serializes refresh attempts. This is source-observed behavior in the inspected commit, not a separate compatibility promise. [Refresh implementation](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/login/src/auth/manager.rs#L2025-L2043) and [guarded refresh](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/login/src/auth/manager.rs#L2368-L2406).
- `account/logout` is the supported disconnect call. Current source attempts best-effort OAuth revocation, preferring the refresh token, and clears local credentials even if remote revocation fails. Consequently, Veduta must not equate a successful local disconnect with guaranteed remote revocation. [Logout behavior](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/login/src/auth/revoke.rs#L1-L75).

The issue's encrypted-vault premise needs revision. Managed login deliberately keeps raw tokens inside Codex storage; App Server has no stable callback for Veduta's vault. A per-connection `CODEX_HOME` located on encrypted storage, or a proven OS keyring configuration, can provide encryption at rest, but that is a Veduta deployment design rather than an OpenAI-provided vault integration.

## Model catalog

Call `model/list`, exhaust its cursor pagination, and use the returned model identifiers and capabilities for that connection. The response includes display metadata, supported reasoning efforts, input modalities, hidden status, and the default marker. `includeHidden: false` is the picker-facing catalog; `true` also returns entries OpenAI intentionally hides from the default picker. [Model-list contract](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server-protocol/src/protocol/v2/model.rs#L40-L53) and [model response fields](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server-protocol/src/protocol/v2/model.rs#L79-L137).

This is the **Codex catalog available to the active client/auth context**, not a general catalog of every model visible elsewhere in ChatGPT or the OpenAI API. “Show the full returned catalog” should mean no Veduta-curated subset of the picker-visible `model/list` result; it should not promise the user's entire ChatGPT model catalog or automatically expose hidden entries. The active-context filtering is source-observed. [Catalog filtering](https://github.com/openai/codex/blob/9d00bb01c0a712fb7c2f5b002bdf33bcc0fc352c/codex-rs/app-server/src/models.rs#L13-L24).

## Audit of the canonical issue

| Premise in Model connections                                             | Finding                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ChatGPT subscription browser/device authorization with automatic refresh | **Documented**, through managed App Server auth. For a remote VPS, device code is the usable path; it is beta and administrator-gated.                                                                                                                                                                                                                                  |
| No raw token or terminal in the PWA journey                              | **Conditional**. Device code satisfies it when enabled. The official fallback when device code is unavailable is local login plus copying the auth cache, which does not satisfy the issue.                                                                                                                                                                             |
| A custom self-hosted Gateway may use the flow                            | **Documented for a custom product integration**, with the inference that a private, authenticated Gateway is an appropriate host. OpenAI separately warns against exposing Codex execution in untrusted or public environments.                                                                                                                                         |
| Subscription inference stays behind the existing Agent loop              | **Unsupported**. The public subscription-capable boundary is a Codex Agent turn, not raw inference. This conflicts with the issue's out-of-scope rule against delegating turns to Codex.                                                                                                                                                                                |
| Provider-side tools can be disabled as a stable contract                 | **Not established**. App Server exposes an Agent with tool and side-effect semantics. Individual tools/features can be constrained, and the process can be sandboxed, but no documented stable “inference only, no tools” API was found. This requires a prototype and a boundary decision, not an acceptance-test assumption.                                          |
| Full account model catalog                                               | **Overstated**. `model/list` returns the active Codex catalog; it is not the general ChatGPT account catalog.                                                                                                                                                                                                                                                           |
| Multiple ChatGPT accounts in one provider adapter                        | **Not a first-class stable App Server auth feature**. Managed login has one active primary auth context. Separate App Server processes with independent `CODEX_HOME` directories are a plausible Veduta design, but that is an inference that needs a prototype, lifecycle limits, and refresh-concurrency tests. Never copy one refresh-token cache between instances. |
| Credentials live in Veduta's encrypted vault                             | **Unsupported as stated**. Managed Codex auth owns file/keyring persistence. Encryption must be supplied below that storage boundary or the requirement must change.                                                                                                                                                                                                    |
| Revoked is a precise upstream lifecycle state                            | **Partially supported**. Refresh failures distinguish invalid/expired/revoked conditions in current source, but the stable public account API does not promise a complete connection-state machine. Veduta must normalize errors conservatively.                                                                                                                        |
| A selected model can be verified with a streamed real call               | **Documented only as a Codex Agent turn** via `thread/start`, `turn/start`, and streamed item/turn notifications. It does not verify a raw `AgentRunner` model provider.                                                                                                                                                                                                |
| Forced access-token expiry can be an end-to-end acceptance test          | **Unstable as a live test**. The public API can request refresh but cannot force expiry. Test refresh deterministically with an adapter fake; keep a real-account smoke test non-destructive.                                                                                                                                                                           |
| No implicit metered or mock fallback                                     | **Veduta policy**, compatible with App Server. App Server errors and rate-limit data can inform it, but failover remains Gateway-owned.                                                                                                                                                                                                                                 |
| Arbitrary personal-Agent workloads are covered by a ChatGPT plan         | **Not promised**. OpenAI documents the SDK for coding-focused Codex threads. Codex access is included across current ChatGPT plans with plan-dependent limits, but that does not turn the subscription into a general-purpose inference API. [Current plan guidance](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan).                  |

## Required change before implementation planning

Resolve one architectural question: **may the ChatGPT adapter delegate a whole turn to Codex App Server, or must it remain a tool-neutral inference provider inside Veduta's Agent loop?**

If whole-turn delegation is accepted, the next decision should be a narrow prototype proving tool isolation, Surface-state injection, streaming translation, Event log coverage, one isolated credential store per connection, and behavior on refresh failure. If inference-only ownership remains mandatory, close the ChatGPT subscription portion as unavailable until OpenAI publishes a supported subscription-backed inference API; do not build against private routes.

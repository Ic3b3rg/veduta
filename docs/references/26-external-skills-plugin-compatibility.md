# Research 26 — External Skill and plugin compatibility

> Checked on **2026-09-30** against primary documentation, source repositories, and the live ClawHub listings, version APIs, and audits. These are documented capabilities and source observations, not hands-on runtime tests. No third-party Skill or dependency was installed or executed.

## Concrete request: paste a ClawHub link into Veduta chat

The supplied [ClawHub page](https://clawhub.ai/pskoett/skills/self-improving-agent) identifies `@pskoett/self-improving-agent`, version `4.0.2`, and advertises `openclaw skills install @pskoett/self-improving-agent`. The author's [README](https://github.com/pskoett/self-improving-agent/blob/b889ef0724c27b7181111b8dd1ac3a108d0b5160/README.md) says the published package is the `self-improving-agent/` subfolder and that this edition is **OpenClaw-only**. The [published version manifest](https://clawhub.ai/api/v1/skills/self-improving-agent/versions/4.0.2?ownerHandle=pskoett) lists `SKILL.md`, a changelog, templates, references, an extraction shell script, and an optional OpenClaw hook with JavaScript/TypeScript handlers and a test. The manifest supplies file hashes, but we did not compare its files byte-for-byte with the [author's source tree](https://github.com/pskoett/self-improving-agent/tree/b889ef0724c27b7181111b8dd1ac3a108d0b5160/self-improving-agent).

The [Skill instructions](https://github.com/pskoett/self-improving-agent/blob/b889ef0724c27b7181111b8dd1ac3a108d0b5160/self-improving-agent/SKILL.md) create `.learnings/{LEARNINGS,ERRORS,FEATURE_REQUESTS}.md`, refer to OpenClaw's `AGENTS.md`, `SOUL.md`, `TOOLS.md` and `sessions_*` tools, and explain that automatic reminders and session-end error detection require separately copying and enabling an OpenClaw hook. The [hook manifest](https://github.com/pskoett/self-improving-agent/blob/b889ef0724c27b7181111b8dd1ac3a108d0b5160/self-improving-agent/hooks/openclaw/HOOK.md) declares `agent:bootstrap`, `command:new`, and `command:reset`. There is no declared provider account or API-key dependency in this package's `SKILL.md` frontmatter; it nevertheless asks the host to perform filesystem operations and may invoke a shell script. Installing the Markdown alone would not provide its hook behavior on Veduta. Even its manual logging and instruction-promotion behavior needs a Veduta-specific compatibility review, since Veduta's SOUL, Space memory, and Chat timelines have different ownership rules. [Veduta glossary](../../CONTEXT.md), [ADR-0026](../adr/0026-skills-may-drive-general-tool-execution.md)

The version `4.0.2` [ClawHub security audit](https://clawhub.ai/pskoett/skills/self-improving-agent/security-audit) reports **Review**, not an unconditional pass. Its A.I.G findings warn about an insufficiently constrained transcript path and best-effort redaction before session excerpts are persisted; the SkillSpector section raises further concerns about scope, persistence, and promotion into future instructions. The audit also says static analysis found no suspicious patterns. These are scanner findings rather than a verified exploit or a guarantee of safety. The author's [changelog](https://github.com/pskoett/self-improving-agent/blob/b889ef0724c27b7181111b8dd1ac3a108d0b5160/self-improving-agent/CHANGELOG.md) says hook changes require copying the hook again and restarting OpenClaw, while `.learnings/` is user data preserved across upgrades.

## Second request: paste the Obsidian Skill and set up its CLI

The [ClawHub record](https://clawhub.ai/steipete/skills/obsidian) identifies publisher `steipete` (Peter Steinberger) and version `1.0.0`. Its [version manifest](https://clawhub.ai/api/v1/skills/obsidian/versions/1.0.0?ownerHandle=steipete) contains just `SKILL.md` (SHA-256 `dc45b522…`) and a generated `skill-card.md`; it includes no executable files. The [published `SKILL.md`](https://clawhub.ai/api/v1/skills/obsidian/file?path=SKILL.md&version=1.0.0&ownerHandle=steipete) declares an OpenClaw/Clawdbot-specific `metadata.clawdbot.requires.bins` entry for `obsidian-cli` and a Homebrew installer `yakitrak/yakitrak/obsidian-cli`. It instructs the Agent to discover vaults through a macOS Obsidian config file and use the CLI for search, create, move, and delete. It has no OpenClaw hook or tool API calls; the primary runtime dependency is the external executable plus access to the right vault. Its metadata is not a generic dependency installer that Veduta can safely obey without adaptation. [ClawHub Skill format](https://docs.openclaw.ai/tools/skills#installer-specs)

The CLI dependency has **drifted since this Skill was published**. The maintained [Yakitrak migration guide](https://github.com/Yakitrak/notesmd-cli/blob/58830c82327b8b34f8e5d52e5a3a7cfa0ad0ab5a/MIGRATION.md) says the former `obsidian-cli` was renamed to `notesmd-cli` after Obsidian released its own official CLI. The current [Homebrew tap migration](https://github.com/Yakitrak/homebrew-yakitrak/blob/26182986480c7c1d8f6dd6c8c1cd767ecb51c1c9/tap_migrations.json) maps `obsidian-cli` to `notesmd-cli`; its [formula](https://github.com/Yakitrak/homebrew-yakitrak/blob/26182986480c7c1d8f6dd6c8c1cd767ecb51c1c9/notesmd-cli.rb) installs a `notesmd-cli` binary. The new [CLI's documented command mapping](https://github.com/Yakitrak/notesmd-cli/blob/58830c82327b8b34f8e5d52e5a3a7cfa0ad0ab5a/README.md#migrating-from-obsidian-cli) changes `set-default` to `set-default-vault` and `print-default` to `list-vaults --default`. The [official Obsidian CLI](https://help.obsidian.md/cli) is a separate `obsidian` command; it requires Obsidian 1.12.7+ and a running desktop app. Therefore the published Skill's declared Homebrew setup **does not appear to supply its required command or fully match its command syntax today**. That is a source-based compatibility finding; no Homebrew install was run.

The [ClawHub audit](https://clawhub.ai/steipete/skills/obsidian/security-audit) displays **Pass** but retains a warning about the unpinned third-party Homebrew tap. A pass label does not verify that the dependency still installs or that a selected vault is accessible. The public record identifies the ClawHub publisher but does not provide a source-repository URL for this exact release. The current [`steipete/agent-scripts` Obsidian Skill](https://github.com/steipete/agent-scripts/blob/d15557c94fa1b92870d6901dbf07615eadf6dd34/skills/obsidian/SKILL.md) instead instructs the official `obsidian` CLI and differs from the published ClawHub text; it must not be treated as the source or update for version `1.0.0` without provenance evidence. On Veduta's VPS profile, a Mac-local vault and desktop URI handler would also require an explicit access path from the Gateway; installing a Markdown Skill cannot create that access. [Veduta architecture](../../ARCHITECTURE.md), [Obsidian CLI guide](https://help.obsidian.md/cli)

The [Agent Plugins v1 specification](https://agent-plugins.org/specification) defines a portable package manifest and components for **Agent Skills and MCP**. It explicitly leaves commands, hooks, agents, rules, and language servers outside v1 because their runtime contracts remain client-specific. [Hermes supports a documented Skills-and-MCP subset](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/#portable-agent-plugins-v1-packages); [OpenClaw recognizes Agent Plugins as compatible bundles](https://docs.openclaw.ai/tools/plugin#understand-plugin-formats). This gives Veduta a useful shared package target, but it does not provide a common ABI for OpenClaw's native JavaScript/TypeScript modules or Hermes's native Python `register(ctx)` modules. An own Veduta catalog could aggregate compatible external sources and Veduta-native packages while checking each package's actual host dependencies; that is a candidate design, not a current feature.

## Implications for Veduta

Veduta's accepted [ADR-0026](../adr/0026-skills-may-drive-general-tool-execution.md) keeps **official** Skills first-party and repository-reviewed. Its v1 package is `SKILL.md` plus focused Markdown references; executable support assets are deferred, and official releases load only first-party Skills. It permits a reviewed Skill to direct Veduta's own general execution tool, but a Skill grants no tool, credential, Space, trigger, or permission. Therefore accepting an arbitrary ClawHub package from chat would **change the accepted trust and distribution boundary** and needs a separate decision before an implementation issue can promise it.

The user's desired contract is now concrete: pasting a ClawHub Skill link should let Veduta inspect the package, obtain approval, then install **and configure every necessary tool or dependency** so the promised behavior works. If Veduta cannot provide a required host hook, tool, command, account connection, or vault path, it should **block installation with the reason and next step**, not leave a partly working Skill installed. This is a product requirement, not a current capability. For either link, a candidate flow would resolve the owner-qualified record; preview publisher, version, provenance gaps, files, scans, dependencies, host behavior, and persistence effects; obtain a Pending decision over the exact artifact and scope; install a pinned copy and approved dependencies; then verify the promised behavior with a safe runtime probe. The Obsidian example specifically needs a separate CLI provenance and live compatibility check **before** dependency installation or vault access. This flow is an **inference and candidate design** based on the user's requirement. Any plugin or MCP installation needs its own host integration and permission model; a Skill link must not bypass those decisions. [ClawHub public API guidance](https://github.com/openclaw/clawhub/blob/main/docs/api.md), [OpenClaw skill security](https://docs.openclaw.ai/tools/skills#security), [Veduta ADR-0026](../adr/0026-skills-may-drive-general-tool-execution.md)

The owner also selected a **Veduta Hub with public community publishing and pre-distribution review in its first release**, plus a user-friendly path to create Veduta-native plugins. The Hub could aggregate compatible external Skills and portable packages while distributing Veduta-native extensions through a separately specified host API. This is a desired outcome, not an implementation decision or a claim of cross-host native-plugin parity. The decision work is tracked in [issue #177](https://github.com/Ic3b3rg/veduta/issues/177).

## Unresolved decisions for a product specification

1. How should Veduta host or adapt third-party executable scripts and lifecycle hooks while preserving its single Agent loop and trust boundary? Until that exists for a package that needs it, the user's fail-closed requirement means installation is unavailable.
2. Should an approved installation be Gateway-wide, visible only in selected Spaces, or selected per Chat timeline? Those are different activation and permission contracts, not a filesystem placement detail.
3. May a third-party Skill propose changes to SOUL, Space INSTRUCTIONS, FACTS, or Agent guidance? The self-improving example explicitly promotes learnings into future instructions; Veduta's [Character-change](../../CONTEXT.md) and [trust](../SECURITY.md) rules already constrain analogous effects.
4. Which foreign-native plugin behaviors, if any, should receive tested Veduta adapters? The owner wants broad reuse and accepts Veduta-native packages where runtime APIs cannot be shared; no blanket OpenClaw/Hermes native-plugin parity has been demonstrated.
5. The ClawHub manifests list versioned files and hashes, but file-level equivalence to the self-improving author's `b889ef0` tree and actual same-turn activation in Hermes/OpenClaw were not independently executed here. The Obsidian example additionally needs proof of a current CLI binary and compatible commands. Verify these in bounded runtime experiments before promising full compatibility.

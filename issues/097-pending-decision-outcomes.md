# 097 — Show truthful Pending-decision outcomes in the PWA and chat

> _This was generated by AI during triage._

## Verified bug

Resolving an Approval Surface currently changes durable state correctly but gives the user no
truthful visible outcome. Approve or Reject archives the Surface and writes audit/Event-log data;
the Gateway has only an `approval.card` creation frame and broadcasts no resolving or terminal
decision frame. The PWA therefore removes the card when its Surface disappears without saying
whether the action executed, was rejected, failed, expired, became stale, or remains in progress.

The same missing feedback lets a later model turn invent status text. In the reported L2 flow the
model claimed that approval had been registered and that execution was still pending, even though
chat has no approval-resolution operation and had received no authoritative outcome.

This is provider-independent. The built-in mock merely makes the missing lifecycle easier to see;
the absent Gateway/PWA outcome path is shared by every Model connection.

## Desired behavior

Every Pending decision publishes an authoritative lifecycle from the daemon. The PWA and chat show
the same resolving and terminal truth regardless of whether the user acted from a Decision Surface,
a notification quick action, or chat. Approval must never be presented as proof that a side effect
succeeded: execution success, rejection, failure, expiry, stale refusal, and indeterminate recovery
remain distinct outcomes.

## Acceptance criteria

- [ ] Each accepted resolution immediately produces visible in-progress or terminal feedback tied
      to the exact Pending-decision id.
- [ ] Terminal feedback distinguishes the workflow's truthful outcomes, including executed,
      rejected, failed/error, expired, stale/refused, and indeterminate where applicable.
- [ ] A decision initiated from UI is reflected in chat and fixed-shell UI; a decision initiated
      from chat is reflected in the Decision Surface/notification state.
- [ ] The pending notification and Decision Surface converge without reload and cannot remain
      visibly pending after a terminal outcome.
- [ ] Reconnect and restart recover authoritative state without duplicating chat feedback or
      resurrecting a terminal decision.
- [ ] User-visible text is derived from daemon state, never from a model assertion, and leaks no
      sensitive payload beyond the already-safe decision summary.
- [ ] Existing audit, Event log, effect idempotency, and workflow-specific outcome guarantees remain
      unchanged.

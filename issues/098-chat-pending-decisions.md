# 098 — Resolve every Pending decision safely from chat

> _This was generated by AI during triage._

## Verified gap

Chat currently has no operation for enumerating or resolving daemon-owned decisions. When a user
types “approve”, “accept”, or “reject”, the model receives ordinary conversation context only. In
the reported flows it re-issued the original L1/L2 action, created another equivalent Approval
card, or claimed that approval had been registered while the real decision remained pending.

This is not a Model-connection parity problem: every provider uses the same chat registry, which
contains the original action tools but no Pending-decision authority. Prompt text cannot safely
substitute for an exact-id, exactly-once daemon resolution.

## Desired behavior

Every daemon-owned Pending decision can be resolved from chat as well as from its Decision Surface.
Chat identifies a current decision, invokes the same exact-id resolution contract as UI, and reports
only the authoritative result. This applies to all decision kinds, not only `send_message` and
`transfer_funds`: trust approvals, Tree proposals, Space proposals, verified updates, and future
registered decision kinds share the behavior.

A bare resolution such as “approve” is accepted only when exactly one pending decision exists in
the current scope. In focused-Space chat that scope is the active Space; in global chat it is the
set of globally visible Pending decisions. If more than one candidate exists, chat presents safe,
distinct choices and changes nothing until the user identifies one unambiguously. An explicit
reference may select a unique visible decision directly.

The current user message must explicitly request the resolution. Prior conversation, Untrusted
content, proactive work, or a model's own suggestion can never supply that authority.

## Acceptance criteria

- [ ] Chat can list and resolve every registered Pending-decision kind through the common contract,
      using the kind's allowed verbs and the exact decision id.
- [ ] A bare approve/accept/apply or reject/decline resolves only the sole pending candidate in the
      deterministic current scope.
- [ ] Multiple or ambiguous candidates produce a safe disambiguation response with zero state
      transition and zero external effect.
- [ ] The reported L1/L2 reproduction no longer creates a duplicate Approval card or repeats the
      original action when the user asks to approve the existing one.
- [ ] A chat response never says that a decision or effect succeeded until the daemon returns the
      authoritative state/outcome from #97.
- [ ] Resolution requires explicit intent in the current `trusted:user` message; Untrusted reads,
      proactive turns, replayed session text, and provider-native tools cannot resolve anything.
- [ ] Chat quick approval uses the prepared input unchanged and never creates an allowlist rule;
      editing or “approve like this from now on” remains available through Review of the Decision
      Surface.
- [ ] Repeated messages, races with UI, reconnect, and already-terminal ids preserve exactly-once
      resolution and return truthful current state.
- [ ] Focused/global scope, ambiguity, injection, provider-parity, and race tests plus `pnpm check`
      pass.

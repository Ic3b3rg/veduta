## What to build

From a selected Mail summary or explicit mail read, let the Agent prepare a reply that remains in
the provider's existing thread. Retrieve the bounded relevant thread context non-mutatingly through
the native Gmail connector or direct Himalaya commands, treat it as Untrusted, then create a durable
editable draft and one Approval card containing the resolved account, recipients, subject, and
body. Original provider content is not copied into the draft Surface.

Sending is L1 Agent behavior. The official Mailbox and connector Skills must create the existing
Pending decision and stop; approval of the exact, possibly edited fields starts one trusted Agent
continuation that performs the send. Typed Gmail tools may enforce the same gate structurally,
while direct Himalaya execution is intentionally governed by the Skill, decision state, tests, and
audit rather than by a command allowlist. Preserve Gmail threadId behavior and standards-based
In-Reply-To/References behavior through connector-specific instructions.

The official flow is idempotent per effect id, checks Sent before retrying an ambiguous command,
verifies the provider result, and reports the authoritative terminal outcome. Fetching context,
drafting, approving, rejecting, or failing to send does not change read state unless the user
separately performed an Explicit mail read.

## Acceptance criteria

- [ ] “Reply that I can attend on Friday” against either provider creates one editable draft and
      one Approval card tied to the exact account, message, thread, Space, and effect.
- [ ] The primary Agent receives only bounded, Untrusted thread context for the current task;
      original bodies and attachments are absent from persistent draft, session replay, Surface,
      Event, notification, Trace, and backup state.
- [ ] Editing recipients, subject, or body in the Approval card changes the exact values sent after
      revalidation; approval never re-generates or substitutes model text.
- [ ] In the official Skill flow, approve starts one send continuation, reject starts none, and
      duplicate actions, reconnects, restarts, timeouts, or indeterminate responses check durable
      effect and Sent state before any retry.
- [ ] Gmail places the reply in the original thread and the Himalaya Skill emits correct
      In-Reply-To and References semantics through its direct command/template procedure.
- [ ] Provider verification and the Pending-decision lifecycle distinguish sent, rejected, failed,
      stale, expired, and indeterminate outcomes without treating approval as proof of delivery.
- [ ] Thread retrieval and reply preparation leave provider read state unchanged unless a separate
      explicit mail read already changed it.
- [ ] Injection, taint, Approval behavior, edited payload, idempotency, threading, native/CLI
      outcome parity, restart, PWA accessibility, and pnpm check pass.

## Out of scope

- Composing a new unrelated message, forwarding, attachments, bulk replies, or automatic replies.
- Mail mutations other than the approved send.
- Resolving or editing an existing Approval card through free-form chat.
- Claiming that the general execution tool makes pre-send Approval structurally unbypassable for
  arbitrary commands or downstream forks.

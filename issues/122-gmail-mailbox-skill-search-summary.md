# 122 — Search and summarize Gmail through the first Mailbox Skill

> _This was generated by AI during triage._

## What to build

Deliver the first complete Mailbox assistant path. In a focused Space, a natural-language request
for Gmail causes the Agent to resolve an explicit Mailbox scope, autonomously load the bundled
first-party mailbox-assistant and Gmail connector Skills, use native Gmail operations available to
the turn, and return concise text plus a protocol-valid Mailbox Surface. The Surface is a bounded
snapshot labelled with its account, resolved query, and last check; it is not an inbox replica.

The scope must resolve the target connection, folders or labels and query, time window, read-state
filter, and result bound that materially affect the request. The Agent asks for clarification
before provider access when current trusted context cannot resolve a material ambiguity. Searching
and summarizing use non-mutating Gmail operations and leave every provider read flag unchanged.

Introduce only the Skill runtime needed by this real feature: strict Agent Skills frontmatter,
optional flat string metadata.veduta.* keys, metadata-first discovery, autonomous loading of one or
more relevant Skills, and at most one explicitly referenced Markdown document loaded on demand per
Skill. Loading a Skill grants no tool or credential; it teaches the Agent how to use capabilities
already offered to the turn. Native Gmail operations remain Veduta-owned tools in this slice, while
the general execution path arrives with the first command-backed connector in #123.

Bundle mailbox-assistant as the provider-independent procedure and a focused Gmail connector Skill
for native-operation semantics. CI targets 100-200 lines, warns above 200, and rejects a SKILL.md
above 500 lines or 5,000 tokens, broken references, unsupported fields, or executable package
files. Raw mail used for summaries goes through the tool-less quarantined extraction boundary; the
primary Agent and durable state receive validated Mail summaries, never original bodies or
attachments in this polished Gmail flow.

## Acceptance criteria

- [ ] From a focused Space, requests such as “show unread receipts from this week” and “summarize
      the last five newsletters” resolve a bounded Gmail query, produce short text plus one
      query-labelled Mailbox Surface, and append only Space-owned safe provenance.
- [ ] An ambiguous account, time boundary, or unbounded request causes clarification before any
      Gmail message endpoint is contacted.
- [ ] Search and summary leave Gmail UNREAD labels byte-for-byte unchanged, including when a result
      is shown in the Surface.
- [ ] No raw body or attachment enters the primary Agent context, session replay, Surface state,
      Event log, notification, Trace detail, memory, or backup.
- [ ] The interactive Agent receives applicable Skill metadata and chooses and loads both the
      mailbox-assistant procedure and Gmail connector without a slash command, picker, or
      user-visible Skill management UI.
- [ ] Missing Skill activation is observable as a routing-quality failure in deterministic tests;
      it never changes which tools are authorized and does not create a parallel runtime gate.
- [ ] Skill validation enforces the strict field, reference, size, token, path, and no-package-
      executable contract, while an unrelated Skill is not injected into the turn.
- [ ] BYOK/fake and ChatGPT-subscription/fake turns receive the same applicable Skills, native Gmail
      capabilities, and persistent outcomes.
- [ ] Gmail API, quarantine, scope, restart, provider-parity, PWA accessibility, and pnpm check pass.

## Out of scope

- Generic IMAP/SMTP accounts.
- Opening a raw message, changing read state, attachments, replies, or recurring Automations.
- Command-backed Skills and the general execution tool introduced by #123.
- Community, user-authored, Agent-authored, downloaded, or executable-package Skills.
- A Skill picker, slash command, Hub, marketplace, or third-party loader.

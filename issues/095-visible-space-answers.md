# 095 — Show visually useful Space answers in Surfaces

## Context

[ADR-0001](../docs/adr/0001-home-first.md) makes chat the editing input for a Home of persistent
Surfaces, and the domain model defines **Surface authoring** as the Agent creating or modifying
Surfaces in response to user intent. Issue 042 completed the focused-Space mechanics: the Agent can
discover and read applicable Surfaces, patch their typed state and Atom trees, or create a new
Surface when none fits.

The remaining decision rule is too narrow. The focused chat contract currently tells the Agent to
author a Surface when a request can _affect Surface content_. A model can interpret a read-only
question as requiring only inspection and prose, even when the answer has a useful visual form.

This happened in a Local VPS turn inside Health on 2026-08-12. For
`"Quante calorie ho mangiato oggi ?"`, the Agent called `list_surfaces`, read the Meals Surface,
estimated a total and per-meal ranges, and answered only in chat. It made no `patch_state`,
`patch_tree`, or `create_surface` call, so Meals remained unchanged. The available answer already
had an obvious structured representation: total estimate, per-meal breakdown, and missing
quantities. The Atom catalog already contains enough components to render it without free-form
HTML.

No existing issue implements this behavior. Issue 042 supplies the required read and authoring
tools but covers mutations requested by the user, not analytical answers that should themselves
become visible state. No matching prior rejection exists.

## Goal

When a focused-Space turn produces a result that is useful to see at a glance, the Agent both
answers in chat and authors that result into the Home. It intelligently chooses among enriching an
applicable Surface, creating a distinct Surface, and removing or replacing a derived composition
that is no longer useful. This remains ordinary Surface authoring over the closed Atom catalog,
not rich content embedded in chat and not domain-specific Gateway logic.

## What to build

- Extend the focused-Space turn contract so Surface authoring applies not only to requests that
  mutate source data, but also to questions whose answer has a useful structured, persistent
  representation. Typical examples include estimates, comparisons, summaries, breakdowns,
  progress, plans, and timelines over Space data. Ordinary conversation and answers with no useful
  visual payoff must remain chat-only.
- Keep the decision with the selected model. The Gateway must not gain a Meals, calorie, nutrition,
  keyword, or intent parser. Deterministic providers may script representative journeys for tests,
  but production behavior stays provider-independent and works through the existing tool registry.
- Before authoring, inspect the complete affected set through the existing focused-Space Surface
  readers. Choose the result's home using these rules:
  - enrich or recompose an existing Surface when it already owns the concern or source data;
  - create a new Surface when the result is a distinct durable concern or no existing Surface fits;
  - update or replace an existing derived region instead of appending duplicate snapshots on every
    follow-up;
  - remove an embedded derived region when a later turn supersedes or dismisses it, and archive a
    separate Agent-authored Surface when that whole Surface is no longer useful.
- Treat removal as recomposition, never source-data deletion. Removing a calorie estimate from
  Meals must preserve the recorded meals. Removing an entire Surface uses archival rather than
  deletion. No background expiry, hidden garbage collection, or time-to-live policy is introduced.
- Preserve Pin and Template behavior. A tree change to a pinned Surface becomes a Tree proposal;
  the Agent never bypasses the Pin. New Surface creation continues through Template matching and
  the existing justification gate.
- Store dynamic visual results in typed Surface state and bind protocol-valid Atoms to it. Reuse the
  existing catalog where it fits; do not add free-form generated HTML or an answer-specific
  rendering channel. Missing inputs, uncertainty, ranges, and caveats must be visible in the
  Surface rather than being hidden behind an unjustifiably exact value.
- Keep the chat answer. It should briefly report the result and the Surface outcome. It may claim a
  Surface changed only after a successful mutation result; if authoring fails or becomes a Tree
  proposal, say so honestly while still providing the useful answer.
- Preserve validation, provenance, trust, Event log, realtime delivery, and Connection parity by
  using the existing Surface tools and AgentRunner boundary. Do not introduce a second write path
  or provider-specific behavior.
- Update durable product documentation so analytical, visually useful focused-Space answers are
  clearly included in Surface authoring. No new glossary term is needed: the confirmed behavior is
  already covered by **Surface authoring**, **Surface**, **Atom**, **Pin**, and **Tree proposal**.

## Acceptance criteria

- [ ] **Confirmed calorie regression:** with Meals containing fesa di tacchino and a breakfast of
      ricotta, cereal, and milk, send exactly `"Quante calorie ho mangiato oggi ?"` inside Health.
      A deterministic primary Model connection calls `list_surfaces`, reads Meals, and completes
      successful Surface authoring before the turn ends. The rendered Meals Surface visibly shows
      a total estimate, a per-meal breakdown, and which quantities are missing; the original meal
      records remain unchanged and the final Surface validates through `SurfaceSchema`.
- [ ] **Chat and Home agree:** the same turn still renders a concise textual answer in chat. Its
      values and caveats agree with the Surface, and it reports the actual mutation, proposal, or
      failure outcome rather than claiming an update that did not commit.
- [ ] **Enrich instead of duplicate:** because Meals already owns the source data, the calorie
      scenario enriches that Surface rather than creating a second Meals or calorie Surface. A
      follow-up with changed quantities updates the existing derived region and state without
      duplicating its Atoms or leaving the previous estimate visible.
- [ ] **Create when the result needs its own home:** in a focused Space with relevant source data but
      no applicable Surface, a request for a durable at-a-glance summary creates one
      protocol-valid Surface through the normal Template gate, renders it live, and links its
      successful creation to the turn's Event log.
- [ ] **Intelligent removal preserves source data:** a follow-up that dismisses or supersedes the
      calorie view removes its derived Atoms and state from Meals, or archives it if the result was
      housed in a separate Agent-authored Surface. Recorded Meals and unrelated Surface content are
      unchanged; no Surface or user data is deleted.
- [ ] **Pin remains authoritative:** when the applicable Surface is pinned, a required tree
      addition, replacement, or removal produces a Tree proposal and leaves the pinned tree
      unchanged until acceptance. A result that fits the existing pinned tree may still update
      typed state through the normal path.
- [ ] **No visual noise:** a deterministic conversational turn with no useful persistent visual
      representation performs no Surface mutation, and repeated analytical follow-ups converge on
      one current composition rather than accumulating answer snapshots.
- [ ] **No domain parser or provider cliff:** production Gateway and Surface code contain no
      calorie-, nutrition-, or Meals-specific language branch. Equivalent scripted behavior works
      through every primary Model connection contract using the same focused-Space tools, and no
      provider-native tool participates.
- [ ] **Runtime proof:** automated integration coverage asserts the tool sequence, committed Event
      log entries, schema validation, source-data preservation, and realtime Surface event. A Local
      VPS browser journey verifies the exact Italian regression, visible enrichment, a follow-up
      replacement/removal, and the simultaneous chat response.
- [ ] `pnpm check` passes, followed by the Local VPS browser E2E job that owns the focused Health
      journey.

## Out of scope

- A nutritional database, authoritative calorie calculation, medical advice, or better estimation
  accuracy. The fixture proves presentation and lifecycle behavior, not nutritional correctness.
- A new Atom type, arbitrary HTML, rich answer cards inside chat, or redesigning the catalog/PWA.
- Hardcoded intent classification, a command grammar, or application logic for Meals or any other
  individual domain.
- Global-chat Space resolution or cross-Space authoring; this issue covers an already focused Space.
- Background cleanup, scheduled expiry, or silent deletion of Surfaces, source records, FACTS, or
  Event log entries.

  the representative fixture.

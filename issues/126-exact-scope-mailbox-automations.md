# 126 — Run exact-scope Mailbox Automations into one linked Surface

> _This was generated by AI during triage._

## What to build

Turn a natural-language recurring mail request into one confirmed, Space-owned Automation whose
durable contract is exactly trigger -> operation -> result. Before creation, present an editable
Pending decision containing the owning Space, account set, schedule and timezone, folders or labels,
provider query, time window, read-state filter, result bound, allowed mutations, and one target
Mailbox Surface. Confirmation may edit those fields; no provider access occurs before it.

Execution starts from confirmation onward and follows the literal confirmed operation. “New since
this Automation” initializes its watermark at confirmation and has no backlog. An explicit query
such as “all unread mail from today at 14:00” evaluates that stated calendar window at the due
occurrence, even when qualifying messages predate confirmation. No universal newest-N window,
inbox scan, hidden cursor, or connector default may widen either form.

Each due occurrence deterministically preloads the newest compatible mailbox-assistant and relevant
connector Skill set. Gmail may use native operations and Himalaya may run direct CLI commands
through general execution. The official Skills follow the literal confirmed scope, preserve unread
state, bound Untrusted output, use quarantined extraction for unattended summaries, and update the
same linked Mailbox Surface. Use the shared Automation outcome contract: unchanged advances
freshness only; meaningful change, failure, and recovery update durable state and the owning
Space's In-app notification without assistant chat, badge, or browser push.

Record every Skill id, version, content hash, dependency/setup state, and compatibility decision in
technical Trace/Automation details only. Interactive turns and Automation runs share this
provenance format. Retain an older Skill version only while an incompatible existing Automation
references it, and remove it after the last such reference disappears. The confirmed Automation
remains the durable trigger, operation, and output contract; direct command semantics are verified
through first-party behavior tests and audit rather than a provider-neutral command parser.

## Acceptance criteria

- [ ] Creating “at 14:00 show all unread mail from today” and “twice daily summarize new
      newsletters” produces editable confirmations whose materially different time semantics are
      visible before acceptance.
- [ ] No message endpoint is contacted before confirmation, between occurrences, while disabled,
      or after cancellation; a manual refresh is a separate explicit user request.
- [ ] “New” starts at the confirmation watermark with no implicit backlog, while an explicit
      calendar/query window is evaluated literally at run time.
- [ ] First-party behavior tests prove every occurrence stays within the confirmed accounts,
      filters, bounds, read-only operation, owning Space, and linked Surface; provider, command, or
      Skill defaults do not widen it.
- [ ] Gmail and Himalaya occurrences leave every matched message unread and produce equivalent
      schema-valid Mail summaries.
- [ ] Repeated runs update one Surface. Unchanged runs update freshness only; changed, failed, and
      recovered runs follow the shared coalesced In-app notification and history contract.
- [ ] No occurrence creates an assistant chat message, Space badge, browser push, duplicate Surface,
      or result in another Space.
- [ ] Interactive and recurring Skill use records every exact id/version/hash plus redacted command
      outcome in Trace, while ordinary chat and Mailbox Surfaces contain no implementation detail.
- [ ] A compatible Skill upgrade is used on the next run; an incompatible referenced version
      remains available until the last dependent Automation is migrated or removed, then is
      garbage-collected.
- [ ] Restart, missed-run policy, disable/cancel, provider parity, scope refusal, version migration,
      notification, Trace, PWA accessibility, and pnpm check pass.

## Out of scope

- Ambient mailbox watchers or polling outside confirmed occurrences.
- Automatic replies, archiving, deleting, moving, labels, stars, spam handling, or folders.
- Community, downloaded, user-authored, Agent-authored, or executable-package Skills.
- Automated mail mutation or send commands; v1 Mailbox Automations are read-only procedures.
- Skill management UI, slash commands, a Hub, or marketplace.

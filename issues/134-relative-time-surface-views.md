# 134 — Keep relative-time Surface views aligned with the user's local calendar

> _This was generated by AI during triage._

## Verified bug

A persistent Surface can label a list, count, summary, plan, or other visible region as “Today”,
“this week”, or another relative calendar window without retaining enough temporal information to
support that claim. Surface state is arbitrary JSON and `FreshnessSchema` records only when and by
whom the Surface was last updated. Nothing requires time-bearing source records to preserve an
occurrence instant or tells the lifecycle when a relative projection stops being current.

The Agent does receive the current user-local date, time, and timezone, and issue #21 established
the shared distinction between recorded and effective occurrence time. The Heartbeat also looks
for time-sensitive Surfaces, but it currently infers them from English words in the Surface title
and is only a safety net. These pieces do not form a reusable contract for relative-time visible
state.

Meals exposed the gap in a 2026-08-20 Loopback browser reproduction: a Surface labelled “Today”
stored rows containing only local `HH:mm` plus meal text, so prior-day rows could not be separated
from current-day rows. Meals is only the representative fixture. The same defect applies to any
Agent-authored Surface showing daily activity, spending, symptoms, tasks, plans, or another
time-scoped projection.

Issue #42 supplies generic Surface discovery and authoring. Issue #95 owns visually useful
analytical answers. Neither establishes temporal integrity for the source state and relative
projections they read. No existing issue implements this horizontal behavior, and the repository
has no matching prior rejection.

## Desired behavior

Whenever visible Surface content makes a relative-time claim, its source state must preserve an
unambiguous occurrence instant and its derived visible values must use the global user timezone.
Recorded time and effective occurrence time remain distinct; a late entry is classified by when it
happened when that information is available.

The Surface must explicitly declare enough validity information for the generic lifecycle to know
when the relative projection expires. At the local calendar boundary, expired content must stop
being presented as current without waiting for another domain record. The implementation may
refresh the projection through the existing timer/event lifecycle or render a clear expired state,
but correctness must not depend on a title keyword, a Heartbeat eventually noticing it, or a
domain-specific mutation.

Source records remain durable. A “Today” table, count, latest value, total, and any other dependent
field may project only the current window, while records outside that window remain available for
later Agent work. Existing records without an occurrence instant must never be silently assigned
to today: keep them as date-unknown source data and show an honest caveat until the user supplies
the missing date.

This is a protocol- and Agent-authoring concern shared by every Space. Reuse the existing timezone,
occurrence-time, Surface validation, Event, timer, and freshness boundaries; add only the smallest
generic validity seam needed. Do not add a Meals parser, a calendar-domain component, title-based
business logic, provider-specific behavior, or a general query language for Atom bindings.

## Acceptance criteria

- [ ] A time-bearing record added through ordinary focused-Space Surface authoring preserves a
      normalized occurrence instant separately from when Veduta recorded the mutation.
- [ ] Two unrelated test Surfaces — the existing Meals fixture and a non-food fixture — use the
      same generic temporal contract to render a “Today” projection, with no production references
      to either domain or its state-key names.
- [ ] With source records on two local calendar dates, every visible value scoped to Today — rows,
      count, latest item, total, and any other bound summary present — includes only the current
      local date while preserving the older source records.
- [ ] Advancing an injected clock across the declared local boundary makes the previous projection
      refresh or become explicitly expired before it can be read as current, without requiring a
      new meal, transaction, task, or other domain event.
- [ ] Window calculation remains correct when the Gateway host timezone differs from the user
      timezone and across daylight-saving gaps and overlaps, using the existing shared timezone
      helpers rather than parallel date arithmetic.
- [ ] Legacy time-bearing state without an occurrence instant remains durable, is excluded from a
      current-window claim unless the user supplies a date, and produces an honest visible/chat
      caveat instead of a guessed classification.
- [ ] Relative validity is explicit in validated data and drives the lifecycle directly; Surface
      titles, prose, state-key names, and the Heartbeat's current keyword heuristic are not an
      authority for temporal correctness.
- [ ] The exact Italian Meals regression still travels through
      `list_surfaces → read_surface → patch_state`, but serves only as one fixture proving the
      shared contract. Chat, visible Surface state, dependent fields, and the authoritative
      mutation outcome agree.
- [ ] Every resulting Surface validates through `SurfaceSchema`; mutations retain provenance,
      append the required Space Event, preserve Pin semantics, and arrive through normal realtime
      delivery with equivalent behavior across primary Model connections.
- [ ] Focused unit/integration coverage plus a Local VPS real-browser journey prove both domains,
      the two-day boundary, timezone/DST behavior, legacy data, source preservation, and
      chat/Home consistency.
- [ ] `pnpm check` and the relevant browser E2E job pass.

## Blocked by

None. Builds on completed issues #11, #16, #21, and #42, and supplies the temporal-integrity
prerequisite for #95.

## Out of scope

- Nutritional lookup, calorie accuracy, medical guidance, or behavior belonging to any individual
  domain; Meals remains only a deterministic fixture.
- A complete historical browsing experience for every Surface.
- A general query/formula language for Atom bindings or a hardcoded relative-time renderer for
  known state shapes.
- Deleting expired source records, changing Pin/Tree-proposal behavior, or changing the L0/L1/L2
  trust model.
